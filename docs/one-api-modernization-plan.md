# One API 现代化改造计划

> 文档状态：规划稿  
> 编制日期：2026-10-07  
> 适用仓库：`one-api_aixlab`

## 1. 背景与目标

当前系统已经具备用户、访问令牌、分组、渠道、模型权限、日志和多种上游适配能力，但核心用量模型仍然围绕“额度”和“倍率”展开。后续改造目标是把系统从额度结算型网关调整为面向课题组/团队的用量观测型网关：

1. 移除用户额度、令牌剩余额度、模型倍率和分组倍率的业务依赖。
2. 统一统计每个用户的输入 Token、输出 Token、总 Token 和请求次数。
3. 增加多 API 格式入口，使同一套渠道能力可以按 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 等协议暴露。
4. 记录上游 Prompt Caching 的读取和写入 Token，并提供可解释的缓存命中率、调用命中率和数据覆盖率。
5. 在不迁移 React + Semantic UI 的前提下，重做前端信息架构、状态反馈和数据可视化，使其更现代、易读、响应式。

本计划只定义目标、边界、阶段和验收标准；具体实施步骤见 [one-api-modernization-implementation.md](./one-api-modernization-implementation.md)。

## 2. 设计原则

### 2.1 客户端协议与上游协议解耦

请求进入系统时先识别客户端协议，再根据渠道能力决定：

1. 上游原生支持该协议时优先原生转发。
2. 上游不支持时使用明确的协议转换器。
3. 无法保证语义等价的字段必须返回明确错误，不能静默丢弃。

### 2.2 用量事实优先于费用推导

系统只把上游返回的真实 Token 用量作为首选数据源。无法获得真实用量时，可以保存估算值，但必须标注来源，不能把估算值伪装成上游报告值。

用量来源统一为：

- `reported`：上游响应明确报告。
- `estimated`：系统根据请求/响应内容估算。
- `legacy`：仅用于识别历史数据，不参与新的 Token 统计。

历史 `used_quota` 不换算成 Token，避免倍率变化造成错误数据。

### 2.3 缓存未报告不等于缓存未命中

缓存字段必须区分：

- `0`：上游明确报告为零。
- `null`：上游没有报告该字段。
- `invalid`：字段存在但不满足数据校验规则。

缓存写入 Token 不等于缓存命中。缓存命中率只由缓存读取 Token 计算。

### 2.4 可回滚、可观测、可渐进迁移

改造应先增加新数据结构和新路径，再切换读写逻辑，最后清理旧代码。数据库旧额度列可以暂时保留以兼容已有部署，但新业务逻辑不得继续依赖这些列。

## 3. 改造范围

### 3.1 包含范围

- 额度扣除、预扣、退款和额度耗尽判断的移除。
- 模型倍率、分组倍率、输出倍率和货币展示的移除。
- 独立 Token 用量记录和聚合查询。
- Chat Completions、Responses、Anthropic Messages 三种 API 格式。
- 非流式、流式、文本、多轮消息、图片、工具调用和工具结果的协议处理。
- Prompt Caching 用量归一化和统计。
- 管理后台 Dashboard、用户、令牌、渠道、日志、模型广场和设置页面改造。
- 协议、用量、缓存和回归测试。

### 3.2 不包含范围

- 不在第一阶段迁移前端框架。
- 不在第一阶段引入深色主题。
- 不实现 Responses 的服务端响应持久化、后台任务和 `previous_response_id` 状态链。
- 不把 One API 自身 Redis/HTTP 缓存误认为上游 Prompt Caching。
- 不承诺所有上游都支持所有协议特性；不支持的特性必须显式报错。

### 3.3 旧数据库兼容性要求

必须支持现有 `oneapi-aixlab` 数据库平滑迁移到新版本，不能要求用户删除数据库后重新初始化。兼容性目标如下：

- 现有用户、令牌、渠道、分组权限、模型权限、选项和历史日志不得丢失。
- 同时兼容 SQLite、MySQL 和 PostgreSQL，以及独立 `LOG_SQL_DSN` 日志库。
- 迁移可以重复执行，失败后可以从备份恢复，不允许留下半完成的不可启动状态。
- 新增表和索引优先采用增量迁移；旧额度、倍率和历史日志列先保留为 legacy，不在首次迁移中强制删除。
- 历史 `quota`/`used_quota` 不能伪造转换为 Token。迁移后这些字段只作为兼容数据保留，新统计从切换点开始记录真实或明确标注的估算 Token。
- 迁移必须提供预检查、备份建议、执行日志、校验报告和回滚步骤。

当前仓库使用 GORM `AutoMigrate` 初始化主要表，并已有 `bin/migration_lab.sql` 等人工迁移脚本。新版本不能只依赖 `AutoMigrate`：协议变化、旧字段兼容、跨数据库 DDL、历史数据校验和幂等执行必须由显式版本化迁移负责。

## 4. 目标数据模型

建议新增独立的 `usage_records` 事实表，至少记录：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `request_id` | 请求级幂等键 |
| `user_id` | 用户 |
| `token_id` | 访问令牌，可为空 |
| `channel_id` | 实际渠道 |
| `model_name` | 对外或归一化后的模型名 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `total_tokens` | 总 Token |
| `cache_read_input_tokens` | 缓存读取 Token，可为空 |
| `cache_write_input_tokens` | 缓存写入 Token，可为空 |
| `request_count` | 请求计数，成功生成请求为 1 |
| `usage_source` | `reported`/`estimated`/`legacy` |
| `cache_usage_status` | `reported`/`not_reported`/`invalid` |
| `stream` | 是否流式 |
| `status` | `success`/`error`/`partial` |
| `created_at` | 请求完成时间 |

记录必须支持按用户、令牌、模型、渠道和时间范围聚合，并以 `request_id` 保证重试或流式收尾不会重复计数。

## 5. API 目标

### 5.1 对外路由

保留已有路由，并新增或完善：

```text
POST /v1/chat/completions
POST /v1/responses
POST /v1/messages
GET  /v1/models
```

所有路由继续使用 Token 鉴权、渠道分发和统一错误处理。

### 5.2 Chat Completions

保留 OpenAI Chat Completions 的消息、图片、工具、工具结果、流式响应和 usage 语义。响应中的缓存信息统一映射到：

```json
{
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 20,
    "total_tokens": 120,
    "prompt_tokens_details": {
      "cached_tokens": 80
    }
  }
}
```

### 5.3 Responses

第一版采用无状态设计：

- 默认 `store: false`。
- 不实现服务端响应存储。
- 不支持 `previous_response_id`。
- 不实现后台任务。
- 支持文本、图片输入、工具调用、工具结果、流式和非流式响应。

Responses 的输入/输出 usage 应保留 `input_tokens_details.cached_tokens` 等明细；不能获得对应明细时仍保存总 Token，但缓存命中率显示为不可计算。

### 5.4 Anthropic Messages

支持：

- `x-api-key` 鉴权。
- Bearer Token 兼容鉴权。
- `system`、多轮 `messages`、文本和图片内容。
- 工具调用及工具结果。
- 非流式和 SSE 流式响应。

Anthropic Prompt Caching 字段归一化为：

- `cache_read_input_tokens` ← `cache_read_input_tokens`
- `cache_write_input_tokens` ← `cache_creation_input_tokens`

## 6. 缓存指标

### 6.1 Token 缓存命中率

按统计周期和筛选条件聚合：

```text
Token 缓存命中率 =
Σ cache_read_input_tokens / Σ input_tokens
```

分母为零、或有效记录没有缓存字段时返回 `null`，不返回 `0%`。

### 6.2 调用缓存命中率

```text
调用缓存命中率 =
cache_read_input_tokens > 0 的有效调用数
/ 已报告缓存数据的有效调用数
```

### 6.3 缓存统计覆盖率

```text
缓存统计覆盖率 =
可计算缓存指标的调用数
/ 已产生模型响应的生成调用数
```

Dashboard 必须同时展示三个指标，避免“没有缓存字段”被误读为“缓存没有命中”。

## 7. 前端目标

继续使用现有 React + Semantic UI 技术栈，不做框架迁移。

### 7.1 全局体验

- 左侧主导航，顶部显示当前用户、环境和快捷操作。
- 统一卡片、表格、标签、确认弹窗和通知样式。
- 完整覆盖加载中、空数据、错误和无权限状态。
- 移动端使用抽屉导航，表格支持横向滚动。
- 重要操作使用二次确认，删除和禁用操作展示明确影响。

### 7.2 Dashboard

首屏展示：

- 总 Token。
- 输入 Token、输出 Token。
- 请求次数。
- 缓存读取 Token、缓存写入 Token。
- Token 缓存命中率。
- 调用缓存命中率。
- 缓存统计覆盖率。

图表支持按日期、模型、用户和渠道查看趋势；所有图表标注统计时间范围和数据覆盖率。

### 7.3 页面清理

用户、令牌、渠道、日志、模型广场和设置页面删除或隐藏：

- 余额。
- 可用额度。
- 充值。
- 模型倍率。
- 分组倍率。
- 输入/输出费用。
- 货币展示。

保留：

- 用户和令牌身份。
- 分组和权限。
- 模型/渠道可用性。
- 有效期、网段限制和状态。
- Token 用量和请求统计。

## 8. 实施阶段

### 阶段 0：基线与契约冻结

- 盘点额度、倍率、usage、日志和前端字段。
- 固定新 API 的请求/响应契约。
- 增加协议矩阵和现有行为回归测试。

### 阶段 1：用量事实层

- 创建 `usage_records`。
- 实现统一 `UsageRecorder`。
- 添加幂等、聚合和覆盖率查询。
- 暂时与旧额度逻辑并行，确认数据完整后再移除结算调用。

### 阶段 2：移除额度和倍率依赖

- 删除预扣、扣除、退款、额度耗尽判断。
- 取消模型/分组倍率参与业务计算。
- 删除 API 和前端中的充值、余额、费用展示。
- 保留数据库旧列和必要兼容读取，但新代码不写入旧额度语义。

### 阶段 3：多 API 格式

- 增加 `/v1/responses` 和 `/v1/messages`。
- 拆分客户端协议解析、上游适配和响应转换。
- 完成非流式后再完成流式。
- 对不可转换特性返回明确错误。

### 阶段 4：缓存命中率

- 扩展统一 Usage 结构。
- 解析三种协议的缓存字段。
- 增加缓存统计 API 和数据覆盖率。
- 在流式和非流式路径使用同一套归一化逻辑。

### 阶段 5：前端现代化

- 先重做布局和基础组件。
- 再调整 Dashboard 和统计图表。
- 最后清理各业务页的额度/倍率字段并补充响应式状态。

### 阶段 6：验证、灰度与收尾

- 完成协议矩阵、数据库迁移、性能和回滚测试。
- 使用旧版本 SQLite、MySQL、PostgreSQL 数据库副本执行迁移，验证核心数据行数、主键、关联关系和关键字段。
- 验证独立日志库迁移，以及迁移中断后重新执行的幂等性。
- 小范围启用新统计，比较请求数和 Token 总量。
- 确认旧额度逻辑没有新写入后，再安排旧字段清理。

## 9. 验收标准

### 用量

- 任意成功请求至少产生一条可追踪的 usage 记录。
- 同一 `request_id` 重试或流式收尾不会重复计数。
- 可按用户、令牌、模型、渠道和日期聚合。
- 输入、输出、总 Token 之间的关系可校验。
- 估算数据和上游报告数据可区分。

### 数据库迁移

- 旧版数据库可以直接升级，不需要清空数据库。
- 用户、令牌、渠道、权限、配置和历史日志的数量及关键字段校验通过。
- 主键和唯一索引没有冲突，逻辑关联仍然有效。
- SQLite、MySQL、PostgreSQL 和独立日志库均完成迁移测试。
- 迁移脚本重复执行不会重复插入、覆盖或破坏数据。
- 迁移失败可以恢复备份，或从失败步骤安全重试。
- 历史额度只保留为 legacy，不被错误解释为新 Token。

### 协议

- Chat Completions、Responses、Anthropic Messages 均可完成文本请求。
- 三种协议均覆盖非流式和流式成功路径。
- 工具调用和工具结果不会丢失参数或调用 ID。
- 不支持的能力返回结构化错误。
- Anthropic 的 `x-api-key` 能正常工作。

### 缓存

- `0`、`null`、`invalid` 语义明确。
- 缓存写入不被统计为命中。
- 命中率使用 Token 加权，不使用单调用简单平均。
- 没有缓存字段时覆盖率下降，但命中率不被伪造为零。

### 前端

- 页面不再显示余额、充值、倍率和费用文案。
- Dashboard 能显示三个缓存指标及统计范围。
- 加载、空、错误、无权限和移动端场景可用。
- 删除用户/令牌等高风险操作有确认反馈。

## 10. 主要风险

| 风险 | 应对 |
| --- | --- |
| GORM AutoMigrate 无法表达复杂数据迁移或跨数据库差异 | 使用显式、版本化、幂等迁移，不把 AutoMigrate 作为唯一方案 |
| 迁移时删除旧列导致历史数据或旧版本回滚失败 | 首次升级只增量新增；旧列延迟到独立清理版本 |
| 独立日志库遗漏迁移 | 对主库和 `LOG_SQL_DSN` 分别执行迁移并分别校验 |
| 中途断电/失败留下半完成结构 | 每步记录版本，使用事务或可恢复步骤，启动前做 schema preflight |
| 旧额度逻辑隐藏在非主请求路径 | 通过全仓搜索、集成测试和日志确认无新扣除 |
| 流式响应无法在结束前取得完整 usage | 以 request_id 暂存并在结束/断开时幂等收尾 |
| 不同协议工具语义不完全等价 | 定义明确转换边界，无法转换时报错 |
| 缓存字段在不同上游中含义不同 | 先归一化并记录原始来源，禁止凭空补零 |
| 历史日志和新 Token 统计口径不同 | 明确标记 legacy，不混入新指标 |
| 前端仍依赖旧字段导致页面崩溃 | 先补充兼容响应，再逐页删除字段 |

## 11. 完成定义

本改造在以下条件全部满足后视为完成：

1. 生产请求不再依赖额度或倍率进行放行、扣除和结算。
2. 用户维度 Token 统计稳定可用，且有可追踪的明细记录。
3. 三种 API 格式的核心文本、工具和流式能力通过协议测试。
4. 缓存命中率、调用命中率和覆盖率可以被正确解释。
5. 前端主要页面完成现代化改造，且不存在过时的额度/倍率文案。
6. 数据迁移、回滚、监控和验收记录齐全。
